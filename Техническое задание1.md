# Технические рекомендации: улучшение проекта и создание полностью нативного приложения (Windows & Android)

**Вывод сразу**: текущий проект — это гибридное приложение на WebView + localStorage (Electron). Ключевые дефекты: **ненадёжное хранение данных** и **сильная связка слоя хранения с UI**. Чтобы реализовать «полностью нативное, локальное хранение, оптимизацию под слабые устройства, плавные анимации 144 Гц», нужно выполнить три базовых преобразования: (1) перевести слой хранения с localStorage на SQLite (Windows) и SQLite/Preferences (Android); (2) заменить или модернизировать Electron на Tauri (Windows) или React Native (Android, полностью нативно); (3) построить систему анимаций на delta-time для адаптации к высокой частоте обновления.


## 1. Диагностика ключевых архитектурных дефектов

### 1.1 Ненадёжное хранение (наивысший приоритет)

Сейчас веб-версия использует `localStorage`, но **в контейнерах WebView (Capacitor/Cordova) система очищает localStorage/IndexedDB при нехватке памяти или длительном неиспользовании**. Это значит, что данные пользователя могут **тихо пропасть** — критический дефект для приложений, работающих с данными (библиотеки промптов, заметки, конфигурации).

**Правильный подход**:
- **Android**: `@capacitor-community/sqlite` — данные пишутся в файловую систему, надёжно и быстро
- **Windows**: `better-sqlite3` (Electron) или `tauri-plugin-sql` (Tauri)
- **Лёгкие пары ключ-значение**: только для настроек — `@capacitor/preferences` (Android) или `electron-store` (Windows)

### 1.2 Зависимость от WebView и нехватка нативных возможностей

Веб-приложение не может реализовать: **системный трей, глобальные горячие клавиши, нативные уведомления, перетаскивание файлов по пути, полный контроль буфера обмена, нативные меню**. Если приложению нужны эти функции — чистое WebView-решение архитектурно не подходит.

### 1.3 Дрейф анимаций на устройствах с высокой частотой

Сейчас анимации на `requestAnimationFrame` реализованы как «фиксированное смещение за кадр» — на экране 144 Гц они будут **в 2,4 раза быстрее**, чем на 60 Гц. Это ключевой баг адаптации к высокой частоте.


## 2. Выбор технологий: расхождение путей Windows и Android

### 2.1 Windows: матрица решений Tauri vs Electron

| Критерий | Tauri v2 | Electron |
|---|---|---|
| **Размер бинарника** | **5–15 МБ** | 80–120 МБ (после сжатия) |
| **Потребление RAM** | **Очень низкое** (системный WebView) | Высокое (встроенный Chromium) |
| **Единообразие рендеринга** | 🟡 Различия системных WebView (WebView2 vs WKWebView) | ✅ Единый Chromium на всех платформах |
| **Автообновление** | Требует доп. настройки | **Встроенный electron-updater** |
| **Язык бэкенда** | Rust (высокая производительность, крутая кривая обучения) | Node.js/TypeScript (знаком команде) |
| **Поддержка SQLite** | `tauri-plugin-sql` | `better-sqlite3` |

**Рекомендация**: если в целевых устройствах есть **слабые Windows-планшеты или старые ПК** (RAM ≤ 4 ГБ) — выбирайте **Tauri v2**. Если единообразие рендеринга критично, а опыта в Rust недостаточно — оставляйте Electron, но **обязательно замените слой хранения на `better-sqlite3`**.

### 2.2 Android: Capacitor vs React Native

**Capacitor** по сути остаётся контейнером WebView и не удовлетворяет требованию «полностью нативно». Его плюс — переиспользование веб-кода, но **потолок производительности заметно ниже нативного**.

**React Native** на Android компилируется в близкий к нативному код, имеет доступ ко всем нативным API (камера, биометрия, SecureStore) и в связке с **локальным SQLite** удовлетворяет требованиям «данные не теряются, производительность приемлема».

**Рекомендация**: Android-версию **отказаться от Capacitor в пользу React Native**. Если нужно во что бы то ни стало переиспользовать веб-код, Capacitor + SQLite — субоптимальный вариант, но придётся принять потери производительности WebView.


## 3. Перестройка слоя данных: от localStorage к SQLite

### 3.1 Единый слой абстракции данных

```
interface StorageAdapter {
  // Запрос
  query<T>(sql: string, params?: unknown[]): Promise<T[]>;
  // Транзакция
  transaction(ops: Array<{ sql: string; params?: unknown[] }>): Promise<void>;
  // Миграция
  migrate(fromVersion: number, toVersion: number): Promise<void>;
}
```

**Реализация Windows**: `better-sqlite3` (синхронный API, очень высокая производительность)
**Реализация Android**: `@capacitor-community/sqlite` или `react-native-sqlite-storage`
**Тесты/веб-деградация**: `sql.js` (SQLite в памяти, WASM)

### 3.2 Стратегия миграции данных

Старые данные лежат в `localStorage` под ключом `promtova-state`. При первом запуске:

1. Прочитать `localStorage.getItem('promtova-state')`
2. Разобрать JSON, выполнить функции миграции по версии схемы
3. Пакетно `INSERT` в SQLite
4. Установить флаг `migration_completed = true`
5. **Не удалять старые данные** — хранить 30 дней для отката

### 3.3 Обеспечение целостности данных

- Использовать **транзакции SQLite** (`BEGIN ... COMMIT`) для атомарности импорта/экспорта/миграции
- Включить **режим WAL**: `PRAGMA journal_mode = WAL` — повышает производительность параллельных чтений/записей
- Периодически выполнять `VACUUM` против фрагментации БД


## 4. Производительность анимаций: адаптация 144 Гц / 60 fps

### 4.1 Основная формула: delta-time анимация

**Не** используйте «фиксированное смещение за кадр»:

```js
// ❌ Нормально на 60 Гц, в 2,4 раза быстрее на 144 Гц
function animate() {
  x += 5; // фиксированное значение
  requestAnimationFrame(animate);
}
```

**Правильно** — считать смещение по **приращению времени**.

```js
let lastTime = 0;
const SPEED = 300; // пикселей в секунду

function animate(timestamp) {
  if (!lastTime) lastTime = timestamp;
  const deltaTime = (timestamp - lastTime) / 1000; // в секунды
  lastTime = timestamp;
  
  x += SPEED * deltaTime; // не зависит от частоты кадров
  element.style.transform = `translateX(${x}px)`;
  
  requestAnimationFrame(animate);
}
```

**Бюджет кадра**: 60 Гц = 16,67 мс/кадр, 144 Гц = **6,94 мс/кадр**, выполнение JS должно укладываться в 60% бюджета.

### 4.2 Анимировать только GPU-ускоряемые свойства

**Предпочтительно**: `transform` (translateX/Y/Z, scale, rotate), `opacity`, некоторые `filter`.

**Избегать**: `left`, `top`, `width`, `height`, `margin` — они вызывают **пересчёт раскладки**, очень плохо по производительности.

### 4.3 Дополнительная оптимизация под высокую частоту

- Использовать **WAAPI (Web Animations API)** вместо ручных циклов rAF для простых анимаций — WAAPI работает в **потоке композитора** и не блокируется главным потоком
- Для сложных последовательностей — **Motion One** или **GSAP**, у них встроена адаптация к высокой частоте и планирование производительности
- Ограничивать число одновременных анимаций: 1000 элементов одновременно вызовут лаги — используйте `stagger` или `limit` на число активных

### 4.4 На Android с React Native

- Использовать **Reanimated 3** (worklets выполняются в UI-потоке)
- Задействовать **`useNativeDriver: true`** везде, где возможно
- Следить за `frameCallback` в **Fabric** (новый рендерер)


## 5. Оптимизация под слабые устройства: адаптация уровня Android Go

Устройства Android Go обычно имеют RAM ≤ 2 ГБ. Официальный фреймворк оптимизации Google описывает цикл **определение KPI → бенчмарк → итерация → регрессионное тестирование**.

**Конкретные меры**:

1. **Ограничить параллельные функции**: при старте загружать только основной UI, некритичные модули инициализировать отложенно
2. **Деградация изображений/ресурсов**: на слабых устройствах загружать ресурсы низкого разрешения, отключать размытие/тени
3. **Оптимизация запросов SQLite**: избегать полного сканирования, индексировать часто используемые поля, использовать `LIMIT` для пагинации
4. **Мониторинг памяти**: на Android использовать `onTrimMemory()` для освобождения некритичных кэшей
5. **Цель по времени запуска**: холодный старт < 3 с (для Go-устройств допустимо до 5 с)


## 6. Карта проекта (эффективный по токенам подход)

Цель `graphify` или аналога — **сократить расход токенов AI-агентами при выполнении задач**. Основная идея: **заменить полное чтение кода структурированным индексом**.

### 6.1 Что должна содержать карта

```
project-map.json
├── modules/           # Список модулей
│   ├── storage/       # Слой хранения
│   │   ├── path: src/storage/
│   │   ├── exports: [StorageAdapter, SqliteAdapter, MemoryAdapter]
│   │   ├── depends-on: [shared/types]
│   │   └── used-by: [store/usePromtovaStore]
│   ├── store/         # Управление состоянием
│   ├── components/    # UI-компоненты
│   └── utils/         # Утилиты
├── symbols/           # Индекс ключевых символов
│   ├── StorageAdapter: { file: "src/storage/types.ts", line: 5, type: "interface" }
│   └── migrate: { file: "src/store/migrations.ts", line: 12, type: "function" }
├── data-flow/         # Потоки данных
│   └── prompt-copy: [Editor -> store -> copy() -> Clipboard]
└── task-history/      # История задач (опционально)
    └── storage-migration: { status: "done", files-touched: [...] }
```

### 6.2 Как использовать карту

Перед задачей агент **сначала читает карту**, определяет нужные файлы и зависимости, **открывает только релевантные файлы** — без полного сканирования. Это снижает расход токенов на типовой задаче на **60–80%**.

### 6.3 Как генерировать

Положить в корень проекта `map.config.ts` и генерировать скриптом:
- Сканировать структуру `src/`
- Разбирать экспорты каждого `.ts`/`.tsx`
- Генерировать `project-map.json`
- Git hook: автообновление карты после каждого commit


## 7. Группы агентов и ТЗ/промпты

### Принцип группировки

По **порядку зависимостей**: сначала нижний уровень, затем верхний, зависящий от результатов нижнего.

### Группа 1: Миграция слоя хранения (наивысший приоритет)

**Доступные модели**: Claude Opus 5.5 / GPT 5.5 Pro / DeepSeek V4 Pro (нужны сильные рассуждения и архитектура)

**Задача**: спроектировать и реализовать интерфейс `StorageAdapter`, дать две реализации — SQLite (Windows/Android) и Memory (тесты/Web). Написать скрипт миграции из `localStorage` в SQLite.

**Артефакты**:
- `src/storage/types.ts` — определение интерфейса
- `src/storage/sqlite.ts` — реализация SQLite
- `src/storage/memory.ts` — реализация в памяти
- `src/storage/migrate.ts` — логика миграции
- Тесты: миграция, транзакции, откат

**Ключевые пункты промпта**:
> «Данные хранятся в localStorage под ключом `promtova-state`, версия схемы — 3. Спроектируй интерфейс StorageAdapter с требованиями: (1) поддержка транзакций SQLite; (2) функция миграции — читать из localStorage и писать в SQLite; (3) при ошибке миграции — откат, без потери исходных данных; (4) реализация in-memory для тестов. TypeScript strict mode.»

### Группа 2: Слой платформенной адаптации

**Доступные модели**: GPT 5.3 Codex / Claude Sonnet 5 (приоритет — код)

**Задача**: реализовать мосты платформ Windows (Tauri/Electron) и Android (React Native/Capacitor).

**Артефакты**:
- `src/platform/windows/` — файловые диалоги, автообновление, системный трей
- `src/platform/android/` — выбор файлов, нативные уведомления, обработка кнопки «назад»
- Логика определения платформы

**Ключевые пункты промпта**:
> «Интерфейс StorageAdapter определён (см. артефакты Группы 1). Реализуй PlatformBridge для Windows (Tauri v2) и Android (React Native или Capacitor), инкапсулируя файловый ввод-вывод, нативные диалоги, получение версии. Требование: единый интерфейс, различия платформ скрыты внутри адаптера, верхний код не знает о платформе.»

### Группа 3: Перестройка системы анимаций

**Доступные модели**: Gemini 3.5 Flash / GPT 5.4 (баланс скорости и стоимости)

**Задача**: перевести текущие анимации на delta-time, подключить WAAPI или Motion One для простых переходов.

**Артефакты**:
- `src/animations/` — утилиты анимации
- Правки вызовов анимации в существующих компонентах
- Тесты высокой частоты (эмуляция 60/120/144 Гц)

**Ключевые пункты промпта**:
> «Текущие анимации используют rAF + фиксированное смещение и дрейфуют на высокой частоте. Нужно: (1) реализовать delta-time утилиты; (2) простые переходы (opacity, transform) перевести на WAAPI; (3) сложные последовательности оставить на rAF, но добавить delta-time; (4) все анимируемые элементы — только transform и opacity, без layout-свойств.»

### Группа 4: UI-онбординг и адаптация под слабые устройства

**Доступные модели**: GPT 5.4 Mini / Gemini 3.7 Flash (экономия, UI-логика проще)

**Задача**: добавить онбординг, упростить UI на слабых устройствах, реализовать деградацию ресурсов.

**Артефакты**:
- Компонент онбординга
- Определение характеристик устройства (RAM, ядра)
- Стратегии деградации: отключение размытия, сокращение анимаций, упрощение списков

**Ключевые пункты промпта**:
> «Целевые пользователи включают нетехнических. Добавь онбординг из 3–5 шагов с объяснением ключевых функций. Реализуй определение возможностей устройства: при RAM ≤ 2 ГБ отключать необязательные анимации и визуальные эффекты. Все тексты онбординга — краткий русский, без терминов.»

### Группа 5: Тестирование и качество

**Доступные модели**: Claude Haiku 4.5 / GPT 5.4 Nano (приоритет — генерация тестов)

**Задача**: дополнить юнит-тесты, интеграционные тесты, бенчмарки производительности.

**Артефакты**:
- Тесты слоя хранения: миграция, транзакции, параллелизм
- Тесты анимации: независимость от частоты кадров
- Бенчмарки: время старта, задержка SQLite-запросов

**Ключевые пункты промпта**:
> «Напиши тесты Vitest для StorageAdapter с покрытием: успешная миграция, откат при сбое в середине миграции, параллельные запросы, проверка WAL. Для delta-time анимации — тест, что при эмуляции 60 Гц и 144 Гц смещение совпадает (погрешность < 1%). Выведи отчёт покрытия.»

## 9. Связь с «Рекомендации по сборке.md»

Тот документ задавал **архитектурные принципы** (Web-first, паттерн адаптеров, разделение ядра и платформы). Этот документ решает **конкретную техническую реализацию**:

- Принцип «StorageAdapter» → здесь конкретизируется как **SQLite**
- Принцип «PlatformBridge» → здесь конкретизируется как **Tauri (Windows) + React Native (Android)**
- Принцип «Web как источник» → здесь добавляется **предпосылка надёжности данных**: веб-версия только для проверки логики, **продакшн-данные — в SQLite**

Точка стыковки: **сначала на веб-версии проверить логику через Memory/SQLite-WASM, затем по этому документу выйти на выбранные платформы.**

Если нужно — могу детализировать промпт любой группы (например, полный код интерфейса `StorageAdapter` или конфиг `tauri.conf.json`).
