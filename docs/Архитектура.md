Технический документ об устройстве приложения: слои, контракты, механизмы надёжности и принятые решения с обоснованием.

Дата: 27.09.2026 · Стек: React 19.2 + TypeScript 5.9 + Vite 7.3, обёртка Electron 43, SQLite через `sql.js` 1.13 (WASM, в памяти), снапшоты в файл/IndexedDB.

## 1. Назначение и ограничения

Личный учёт личных финансов: операции, регулярные платежи с подтверждением по месяцам, бюджеты, цели, инвестиции, сканирование чеков. Один пользователь, одна база, русский интерфейс, работа офлайн.

| Сознательно не делается | Почему |
|------------------------|--------|
| Облачные бэкапы, авторизация, синхронизация | Модуль Яндекс Диска удалён: OAuth-токен лежал в `localStorage` рядом с финансовыми данными, а под `file://` `redirect_uri` превращался в `null`. Остались локальный экспорт/импорт JSON и файл SQLite (`src/lib/storage.ts:145-149`) |
| Многопользовательский режим, сервер, API | Бэкенда нет; вся модель — один документ `AppData` (`src/lib/types.ts`) |
| Автообновление приложения | Нужен `electron-updater` и сервер релизов; место подключения — слой `PlatformBridge` |
| Нативная БД (better-sqlite3, tauri-plugin-sql) | Интерфейс `SqlDriver` (`src/storage/types.ts:33-56`) написан так, что замена локальна, но нативных драйверов среди зависимостей нет |
| React Native / Tauri-реализация | Требует внешнего тулчейна (Rust/Cargo). Android-мост при этом переписан и работает — слой доступа к платформе не заготовка |
| Подпись установщика и APK | Нет сертификата подписи кода для Windows, ключ Android самоподписанный. SmartScreen предупредит, Google Play ключ не примет без Play App Signing |

Граница прочности: любой сбой хранилища переводит приложение в режим `memory` с явным предупреждением, а не в тихий сбой.

## 4. Хранилище

### 4.1 Движок, снапшот, цепочка фолбэков

Движок — `sql.js`: тот же SQLite, скомпилированный в WebAssembly, но **вся база живёт в памяти** рендерера. Отсюда главное свойство: дисковое хранение — это снимок всего образа, который `SqliteStorage` делает через `SqliteSqlDriver.export()` после каждой успешной транзакции (`src/storage/sqlite.ts:554-573`). `createSnapshotStore()` (`src/storage/snapshots.ts:279-286`) выбирает хранилище:

```
window.electronAPI.loadDb есть  →  ElectronSnapshotStore      kind:"file"         ← Windows
иначе indexedDB есть            →  IndexedDbSnapshotStore     kind:"indexeddb"   ← браузер, WebView
                                   с резервом LocalStorageSnapshotStore
иначе localStorage есть         →  LocalStorageSnapshotStore  kind:"localstorage"
иначе                            →  MemorySnapshotStore        kind:"memory"
```

Смысл фолбэка IDB → localStorage: `IndexedDbSnapshotStore.load()` при пустом IDB спрашивает резерв (там может лежать более свежая копия, если предыдущая запись в IDB не прошла), а `save()` при успехе очищает резерв, при отказе — пишет в него и удаляет устаревшую запись из IDB (`snapshots.ts:173-206`). Запись в IDB считается успешной только на `tx.oncomplete`, отказ — на `tx.onerror`/`tx.onabort`; открытие ограничено таймаутом 3000 мс (`snapshots.ts:20`, `:130-149`).

| | Windows (Electron) | Мобильный WebView / браузер |
|---|---|---|
| Где байты | файл `nexus-data.sqlite` в `app.getPath("userData")` = `%APPDATA%\nexus-finance\` | `indexeddb://nexus-finance/db.sqlite` |
| Кто пишет | `electron-main.cjs` (`save-db`) атомарно: `.tmp` → `fsync` → `rename` → `fsync` каталога (`:153-188`) | сам рендерер |
| Что переживает | перезапуск, очистку кэша браузера | перезапуск; **но стирается при очистке данных приложения ОС** |

### 4.2 Схема

`SCHEMA_VERSION = 1` (`schema.ts:9`). Одна таблица на коллекцию `AppData` плюс служебная `meta`. Каждая таблица содержит колонки коллекции и дополнительную колонку `doc` с полным JSON записи — она гарантирует round-trip без потерь при добавлении полей (`schema.ts:171-183`).

| Таблица | Колонок (с `doc`) | Индексы |
|---------|-------------------|---------|
| `transactions` | 11 | `date`, `category`, `status`, `sourceId`, `(date, category)` |
| `subscriptions` | 9 | `billingDay`, `period` |
| `fixed_payments` | 9 | `payDay`, `category` |
| `budgets` | 5 | `category` |
| `goals` | 7 | `deadline` |
| `investments` | 7 | `ticker` |
| `pending_payments` | 13 | `dueDate`, `sourceId`, `status` |
| `skipped_payments` | 9 | `skippedDate`, `sourceId` |
| `meta` | 2 (`key`, `value`) | — |

Итого 17 индексов — совпадает с `environment.indexes` в `benchmarks/storage.json`. Числа сверены с `scripts/check-desktop-db.mjs:78-87`, который импортирует `src/storage/schema.ts` напрямую (`:90-110`) и падает на зашитую копию только если импорт не удался. В `meta` живут `schema_version`, JSON настроек (`settings`: `currency`, `theme`, `fontScale`) и флаги миграции/онбординга.

### 4.3 Запись, очередь, целостность

Все операции записи проходят через очередь `enqueue()` (`sqlite.ts:459-466`): `write`, `clear`, `setFlag`, `transaction` и `compact` ставятся в цепочку промисов, пока не завершена предыдущая. Причина прямо в коде (`:354-364`): без общей очереди два автосохранения подряд оказываются в одной незавершённой транзакции — чужой `ROLLBACK` откатывает уже возвращённый `true`, а удаление «устаревших» строк сносит только что записанное. Внутри открытой транзакции (`txDepth > 0`) операции идут **напрямую**, иначе внешняя транзакция ждала бы саму себя; вложенный `transaction()` выражается через `SAVEPOINT` (`:140-164`, `:472-477`, `:532-552`).

`write(data)` — дифф-запись по `id` (`:366-402`): строки без строкового `id` отбрасываются с явной ошибкой в консоль (иначе они размножались бы при каждом сохранении), существующие `id` читаются, пропавшие удаляются чанками по 400 (`DELETE_CHUNK`, `:58`), остальные пишутся одним `prepared statement` на коллекцию через `runBatch` (`schema.ts:215-221`, `sqlite.ts:125-138`).

Прочие гарантии:

* **Размер** считается как `PRAGMA page_count × page_size`, а не через `export()` — экспорт пересобирает весь образ (`sqlite.ts:429-453`).
* **Снапшот не сохраняется внутри транзакции** (`persist()` выходит при `txDepth > 0`, `:557`): `db.export()` закрывает транзакцию. Снапшот пишет внешняя транзакция сразу после `COMMIT` (`:509-512`).
* **`VACUUM`**: `compact()` → `compactNow()` (`:485-496`) идёт через очередь, но внутри `clear()` вызывается напрямую (`:423`) — иначе встал бы в очередь за самим собой. После удаления всех данных сжатие выполняется автоматически, в настройках есть кнопка «Сжать базу (VACUUM)» (`src/views/Settings.tsx:273-284`).
* **Очистка служебных флагов**: `clear()` удаляет из `meta` всё, кроме четырёх ключей — `schema_version`, `settings`, `migration.legacy.v1`, `migration.legacy.v1.migratedAt` (`:415-418`). Флаги миграции переживают очистку намеренно: иначе следующий запуск прочитал бы старый ключ из `localStorage` и вернул удалённые данные.
* **Битый снапшот** при старте не роняет приложение: `open()` ловит ошибку импорта и делает `reinit()` (`:264-273`).
* **Защита от базы из более новой версии**: если `schema_version` больше `SCHEMA_VERSION`, чтение разрешено, а запись запрещена — выставляется `locked`, и `assertWritable()` (`:498-500`) бросает исключение на каждой операции записи (`:275-283`). Иначе старый DDL разъётся с миграциями новой версии.
* **`persistent` честный** (`:229-232`): `false`, если снапшот только в памяти **или** последняя запись провалилась. Ошибка записи не проглатывается: `lastPersistError` попадает в `describeStorage()` и в настройки, UI не показывает ложное «сохранено» (покрыто тестами, блок «Честность признака persistent»).

### 4.4 Миграции

**DDL-миграции схемы.** `MIGRATIONS` в `schema.ts:258-264` — пока один шаг `base-schema` (v1). Шаги идемпотентны (`IF NOT EXISTS`), применяются внутри транзакции драйвера и одной строкой пишут новую версию в `meta` (`sqlite.ts:166-169`); при `current < SCHEMA_VERSION` это делает `open()` (`:284`).

**Перенос наследия из `localStorage`** — `src/storage/migrate.ts`: кандидаты `STORAGE_KEY` (`nexus.data.v1`), `nexus.data`, `promtova-state` (`:20`, `constants.ts:6`); перебор **всех** ключей с выбором первого разобравшегося (`collectCandidates`, `:88-103`); импорт в одной транзакции — `write(data)` плюс два флага (`:223-240`); если в базе уже есть записи, данные не перетираются, только ставится флаг (`:202-219`); статусы `imported` / `already-done` / `no-source` / `invalid-source` / `failed` (`:22`). Срок отката 30 дней (`LEGACY_KEEP_DAYS`, `:17`) считается по метке `migration.legacy.v1.migratedAt`; `purgeLegacySource()` вызывается при каждом старте (`index.ts:47-50`) и удаляет исходный ключ только если срок истёк **и** флаг миграции стоит (`:146-152`) — после удаления метка пишется пустой строкой, `getFlag` возвращает `""`, что равносильно отсутствию флага, и резервная копия перестаёт показываться в настройках.

Нормализация входа (`src/lib/normalize.ts:19-53`) принимает документ **без** `transactions`: достаточно хотя бы одной узнаваемой коллекции или одного из полей настроек — так не теряются подписки и цели, когда потерялся только журнал.

### 5.2 `src/hooks/AppProvider.tsx`

Единственный владелец `AppData`. Ключевые решения:

* **Загрузка** (`:97-127`): `storageService.load()`; `null` → `buildSeed()`; успех → данные. Ошибка чтения — **не** `null`: состояние остаётся пустым, выставляется `loadBlocked`, показывается тост «Данные не перезаписаны». Это главная защита от цепочки «ошибка чтения → демо-данные → автосохранение затерло базу». `retryLoad` (`:130-141`) снимает блокировку, кнопка в настройках — `Settings.tsx:304-306`.
* **Автосохранение** (`:154-166`): дебаунс 500 мс, отменяется при `isLoading` и при `loadBlocked`. Единственный путь наружу — `storageService.save`.
* **Очистка данных** (`:513-524`): сначала `await storageService.clear()`, и только потом `setData(emptyData())`. Раньше `clear()` был fire-and-forget, и отложенное автосохранение возвращало удалённое обратно.
* **Автогенерация pending** (`:178-198`): эффект пересчитывает `generatePending` при изменении подписок, платежей, pending и переносов, и чистит переносы с `carryOver` за текущий месяц.
* **Удаление** (`:236-350`): `deleteTransaction` для операций регулярных источников вызывает `deleteTransactionCompletely` либо `deletePaymentSourceCompletely` (`withSource = true`); `deleteRecurringSource(kind, id, mode)` реализует режимы `carry` / `keep` / `all`.
* **Экспорт/импорт** идут через `platform()` (`:486-511`), а не через `URL.createObjectURL` в UI: в Electron это нативный диалог и запись файла. **Тема и масштаб** вешаются на `<html>` в отдельных эффектах (`:169-175`).
* **Смена вкладки сбрасывает прокрутку** (`:200-209`): прокручивается не окно, а `<main class="app-main">` — корневой контейнер имеет `h-screen` + `overflow: hidden`, поэтому `window.scrollTo` был пустым вызовом, и при переходе на вкладку из 3–5 экранов пользователь оказывался в середине с сохранённой позицией предыдущей вкладки.

### 5.3 Знаки валют: почему их нельзя получить из `Intl`

`src/lib/utils.ts:88-152`. Первая побытка на реальном устройстве: **знак рубля ₽ (U+20BD) в системном шрифте телефона отсутствует**, и WebView рисовал вместо него прямоугольник — суммы выглядели как `557 885 ▯`. Подменить знак после форматирования невозможно: `Intl.NumberFormat` со `style: "currency"` подставляет символ валюты сам и не отдаёт его для правки.

Отсюда решение из трёх частей:

| Часть | Что | Зачем |
|-------|-----|-------|
| `hasGlyph(ch)` (`:100-125`) | Измеряет ширину символа в канвасе шрифтом, которым реально рисует страница (`getComputedStyle(document.body).font`), и сравнивает с шириной заведомо отсутствующего глифа U+FFFF: у «плашки» ширина одинакова для всех недостающих символов. Результат кэшируется в `glyphCache` — измерение создаёт канвас. Если канвас недоступен (тестовая среда без DOM), считается, что глиф есть: ломать форматирование из-за проверки нельзя | Никакого списка шрифтов и никакой таблицы символов: проверка отвечает на вопрос «что будет нарисовано», а не «что записано в Unicode» |
| `readSymbol(currency)` (`:136-139`) | Возвращает `CURRENCIES[currency].symbol`, если глиф есть, иначе текст из `CURRENCY_TEXT` (`RUB → "руб."`, `USD/EUR/GBP → "USD"/"EUR"/"GBP"`). Экспортируется наружу, потому что символ показывается не только в суммах | Единая точка решения для всех экранов: `Settings.tsx:145` выводит символ валюты через неё же |
| `formatNumber(n, currency, compact)` (`:141-152`) | Форматирует **число** (`Intl.NumberFormat("ru-RU")` без `style: "currency"`) и дописывает знак из `readSymbol()` сам: `` `${number} ${symbol}` `` | Единственный способ обойти подстановку символа. Побочный эффект: разделителем числа и знака становится обычный пробел — это записано в коде явно |

Проверено на устройстве: вместо «плашки» выводится «557 885 руб.». Символ
валюты — тоже глиф, поэтому проверка общая и для `Settings`.

### 6.1 Контракт и выбор моста

`src/platform/types.ts`. Интерфейс `PlatformBridge` описывает **8 методов** и 3 readonly-поля (`kind`, `native`, `features`) — всего 11 членов. Методы: `appVersion()` (в Electron — `app.getVersion()`, в Android — `App.getInfo().version`, в web — константа `1.0.0`), `storageHint()` (человекочитаемое описание, где лежат данные, для настроек), `openDataFolder()`, `pickTextFile(accept?)` (`null` — пользователь отменил), `saveTextFile(name, content)`, `notify(title, body?)`, `onBackButton(handler)` (возвращает отписку), `setTray(visible)`. Поле `features` — флаги `tray`, `nativeDialogs`, `notifications`, `backButton` и необязательный `dataFolder`: значение `false` — честный отказ, в котором пункт настроек прячется, а отсутствие поля трактуется как «возможность есть».

> Сверка с кодом: в `PlatformBridge` (`src/platform/types.ts`) **8 методов** и 3 поля-«только чтение» (`kind`, `native`, `features`) — 11 членов. Раньше в отчёте по ТЗ стояло «12 методов»; цифра исправлена на 8. Шесть неработающих методов android-моста подтверждены были построчно и с тех пор исправлены (раздел 6.3).

Выбор моста — `platform()` (`src/platform/index.ts:23-30`): `windows` + `window.electronAPI` → `createElectronBridge()`, `android` → `createAndroidBridge()`, иначе `createWebBridge(kind)`. Мост создаётся один раз и кэшируется. Мост Windows никогда не бросает исключений: если в preload нет нужного канала (старая сборка, тестовая среда), вызывается веб-реализация (`electronBridge.ts:33-68`). Сравнение мостов: `native` — `true` / по `Capacitor` / `false`; `tray` и `nativeDialogs` — `true` только у Windows; `notifications` — `true` у Windows и веба, у Android по наличию плагина; `backButton` — `true` только у android и тоже по наличию плагина; `dataFolder` — необязательное поле, объявленное у Android-моста как `false`.

### 6.3 Android-мост: как устроен и что делает

`src/platform/android/capacitorBridge.ts` — 344 строки под Capacitor 8 (раньше
была заготовка на 68 строк, обращавшаяся к `globalThis.Capacitor`; Android-проекта
в репозитории не было, и 6 из 8 методов контракта работали молча и неверно —
история в `docs/Выполнение-ТЗ.md` §7а). Сейчас проект собирается:
`capacitor.config.ts` + каталог `android/`, мост переписан, все 8 методов
работают или честно отказывают.

Три правила файла, из которых следует всё остальное: наружу не выбрасываются
исключения; `true` означает, что действие действительно произошло; каждая ошибка
пишется в `console.error` с префиксом `NEXUS` — иначе «молчаливо неработающая
функция» вернётся в следующей сборке.

| Метод | Как реализован | На что опирается |
|-------|----------------|-----------------|
| `onBackButton` | `App.addListener("backButton", …)`; если приложение вернуло `false` — `window.history.back()` при `canGoBack`, иначе `App.exitApp()`. Отписка синхронная, но подписка нативная: если отписаться раньше, чем пришёл `PluginListenerHandle`, подписка снимается сразу, как только он появится | `capacitor.config.ts` → `App.disableBackButtonHandler: false`. **Это не «не настроено», а требование:** при `true` нативный `AppPlugin` вообще не создаёт `OnBackPressedCallback`, и кнопка «Назад» перестаёт доходить до JS вместе со всей логикой `usePlatformBackButton` |
| `notify` | `@capacitor/local-notifications`: `checkPermissions` → `requestPermissions` при необходимости, затем `schedule` с растущим `id` (одинаковый `id` перезаписывает предыдущее уведомление) и `isExactNotification: false` | Разрешение `POST_NOTIFICATIONS`; по умолчанию плагин планирует уведомление «точным будильником» и на Android 12+ открывает лишний экран |
| `saveTextFile` | `@capacitor/filesystem`: имя приводится к одному сегменту пути (`safeFileName`), затем попытки `Directory.Documents` → `Directory.External`; из папки приложения файл отдаётся `@capacitor/share` с приведением URI к `file://` | `Directory.Data` **намеренно не используется**: в `res/xml/file_paths.xml` нет `files-path`, и `Share` упал бы. `<a download>` в WebView не сохраняет файл — в `@capacitor/android` нет ни `setDownloadListener`, ни `onDownloadStart` |
| `appVersion` | `App.getInfo().version` — то есть `versionName` из `AndroidManifest.xml`, а не константа бандла | Читается при старте; при отказе — `console.error` и откат на web-мост |
| `openDataFolder` | честно `false` | У WebView нет пользовательской папки. В `Settings.tsx` пункт скрывается по `features.dataFolder !== false` (поле необязательное, чтобы не ломать типы мостов, которые его не описывают) |
| `storageHint` | константа `indexeddb://nexus-finance/db.sqlite (внутри приватного хранилища приложения)` | Схема хранения — `src/storage/snapshots.ts`. Файла `sqlite://nexus-finance.db` на Android не существует: база лежит записью в IndexedDB |
| `pickTextFile` | делегирует в `readTextFile` браузерной реализации | `<input type="file">` обрабатывает `WebChromeClient` контейнера, системный выбор файла открывается |
| `setTray` | честно `false` | Системного трея на Android нет |

`native` вычисляется по `Capacitor.isNativePlatform()`; наличие плагина
проверяется через `hasNativePlugin()` — она смотрит и зарегистрированные
JS-обёртки, и список, объявленный нативным мостом, потому что в обычном
браузере на Android у веб-реализаций есть своя регистрация.

`features` отражают реальность, а не пожелания: `tray: false`, `nativeDialogs: false`
(нативный выбор файла открывает сам WebView), `notifications` и `backButton` —
по наличию плагина в сборке, `dataFolder: false`.

> **Уточнение после проверки на устройстве.** Мост `notify()` исправен, но
> **приложение его нигде не вызывает**: `src/platform/*` не содержит ни одного
> вызова `platform().notify()` / `bridge.notify()`. Все сообщения пользователю идут
> внутренними всплывающими подсказками — функцией `notify()` из `AppProvider`
> (одноимённая, но к мосту отношения не имеет). Разрешение
> `POST_NOTIFICATIONS` объявлено, запроса не происходит, системных уведомлений не
> приходит. Пока это так, `README.md` и `docs/Решение-проблем.md` §8 не обещают
> уведомлений.

### 6.4 Кнопка «Назад», стек оверлеев и единая нативная подписка

Проверено на устройстве: до этих правок диалоги закрывались только `Escape`,
которого на телефоне нет, и «Назад» сразу уводил с приложения. Разбор решения.

**Ограничение контейнера, из которого следует всё остальное.** Capacitor раздаёт
одно нативное событие `backButton` **всем** подписчикам (`@capacitor/core`,
`notifyListeners: listeners.forEach`), а `onBackButton` в мосте после вызова
обработчика смотрит на результат: вернувший `false` зовёт
`passBackToSystem(event.canGoBack)` (`capacitorBridge.ts:179-188`), то есть либо
`window.history.back()`, либо `App.exitApp()`. Значит **вторая нативная подписка
недопустима**: два
независимых обработчика означали бы, что «Назад» выполнит оба действия, и
закрытие верхнего диалога дополнительно выкинет из приложения.

**Стек оверлеев** (`src/hooks/useOverlayStack.tsx`) — потому обработчик в
приложении один и он должен сам решить, кому достанется нажатие. Правила
(записаны комментариями в файле):

| Решение | Почему |
|---------|--------|
| Список в `useRef`, а не в `useState` | Решение принимается один раз — на нажатии, и обработчик должен увидеть состояние на момент нажатия, а не снимок на момент рендера. С `useState` подписчик поймал бы старый массив и закрыл уже закрытый диалог. Плюс `ref` не участвует в сравнении зависимостей: ни стек, ни нативный слушатель не могут переподписаться из-за смены идентичности |
| Отдельный счётчик `version` | Список лежит в `ref`, поэтому без счётчика React не узнал бы об изменениях. Идентичность значения контекста меняется только по нему |
| `useOverlay(active, closer)` кладёт закрывалку и снимает её тем же cleanup-ом, что и подписку на событие | Закрывалка читается через `closerRef` — новая стрелка `onClose` на каждом рендере (у `Modal` это так) не переподписывает стек. Отписка идемпотентна, иначе второй вызов (второй прогон эффектов) снёс бы чужой диалог с той же закрывалкой |
| Верхний из стека закрывается первым | Единственное правило выбора жертвы — порядок открытия, как в браузере и в самом Android |

В стек встают все окна на `Modal` (вместе с `ConfirmDialog` и модалкой
транзакции), онбординг, камера сканера, панель выделения и фильтров в журнале.

**Цепочка «назад»** (`src/App.tsx:65-100`), строго по убыванию приоритета:
верхний оверлей из стека → модалка транзакции (страховка: её состояние в
контексте меняется раньше, чем отработает эффект регистрации) → возврат на
«Обзор» с любого раздела → на «Обзоре» `canHandle` возвращает `false`, и мост
выпускает нажатие в систему. Переставлять 1 → 3 нельзя: сначала закрывается то,
что поверх экрана, и только потом уходит сам экран.

**Одна нативная подписка** (`src/components/AppShell.tsx:44-100`). Шторке «Ещё»
нужен ещё один, более приоритетный обработчик, но подписаться второй раз нельзя,
поэтому `onBackButton` перехватывается **на уровне модуля**: нативная подписка
заводится в `installBackRouter()` (вызывается при загрузке модуля, то есть **до**
`useEffect` в `App.tsx` — иначе единственной гарантией был бы порядок эффектов),
а обработчик приложения кладётся в слот `backRouter.app`. На нажатии сначала
спрашивается `backRouter.shell` (шторка), и только если она не ответила —
обработчик приложения. Пока шторка закрыта, поведение «назад» ровно прежнее.
Мост — синглтон, подписка живёт столько же, сколько приложение, поэтому и снимать
её не нужно.

**Шторка «Ещё»** (`BottomSheet` в `src/components/ui.tsx:464-576`) — девять
разделов, которые не помещаются в ленту. Приём не придуман: вход — CSS-анимация
`.sheet-panel` (как `slide-up` у `.modal-panel`), выход — те же WAAPI-анимации и
тот же таймер, что в `Modal` (`collapseOutKeyframes`, `MODAL_EXIT_MS`), плюс
деградация через `resolveMotionPlan`. Разметка — как у диалога: `role="dialog"`,
`aria-modal="true"`, `aria-labelledby`, `FocusTrap`, затемнение, крестик,
`Escape` на десктопе, «ручка» `.sheet-grip` (`aria-hidden`) и
`overscroll-behavior: contain` — список разделов не утягивает страницу под шторкой.
Текущий раздел помечен галочкой, список берётся из `NAV`, поэтому новый раздел
появляется в шторке сам. В стек оверлеев шторка **не встаёт** намеренно: её
закрывает приоритетный слот `backRouter.shell`, а две подписки на `backButton`
недопустимы.

**Проверка на устройстве:** шторка → модалка транзакции → возврат на «Обзор» →
выход из приложения, вся цепочка отрабатывает по порядку.

## 7. Межпроцессное взаимодействие в Electron

**Условия окна** (`electron-main.cjs:385-399`): `sandbox: true`, `nodeIntegration: false`, `contextIsolation: true`, `preload: preload.cjs`. Рендерер — собранный `dist/index.html`, открытый через `win.loadFile()`, то есть по протоколу `file://`. Что это накладывает на preload (`preload.cjs:1-19`): доступны только `require("electron")` и встроенные модули песочницы (`events`, `timers`, `url`) — `fs` и `path` недоступны, вся работа с диском делается в главном процессе; наружу отдаётся только `contextBridge.exposeInMainWorld("electronAPI", …)` — набор функций, `ipcRenderer` и внутренние переменные в мир страницы не выходят; имена каналов обязаны совпадать с `ipcMain.handle` (список продублирован в комментарии `preload.cjs:12-19` как защита от рассинхронизации), а их типы описаны в `src/lib/electronApi.ts`.

| Канал (9) | Запрос | Ответ | Что происходит |
|-----------|--------|-------|----------------|

### Почему ошибка чтения БД не должна превращаться в «базы нет»

Цепочка: `SqliteStorage.open()` (`sqlite.ts:251-285`) → `snapshots.load()` → `ElectronSnapshotStore.load()` → IPC `load-db`. Контракт различает три исхода: `null` — файла нет, первый запуск, можно начинать с нуля; исключение — файл есть, но не читается (нет прав, файл занят, повреждён); успех — `Uint8Array`. `open()` ловит исключение, записывает `readError`, ставит `lastPersistOk = false` и **ничего не импортирует**. Дальше `AppProvider` получает `null` только в первом случае; во втором `storageService.load()` пробрасывает ошибку (`lib/storage.ts:44-59`), и проваз загрузки ставит `loadBlocked`.

Если бы ошибка чтения возвращалась как `null`, цепочка отработала бы так: демо-данные (`buildSeed()`) → дебаунс 500 мс → `save()` → `db.export()` пустой базы → `save-db` → атомарная перезапись существующего файла. Пользователь увидел бы «приложение работает», а данные были бы стёрты. Поэтому и `false` в `save-db` превращается на стороне рендерера в исключение, а не игнорируется.

Дополнительные меры в главном процессе: `requestSingleInstanceLock()` (`:484-487`) — второй экземпляр закрывается, иначе два процесса писали бы в один файл БД и последний снапшот перетирал бы первый; `setWindowOpenHandler` → `deny` и запрет `will-navigate` для всех URL вне каталога приложения (`:83-91`, `:408-418`); журнал `app.getPath("logs")/nexus-finance.log` с ротацией на 2 МБ в `.old` (`:25`, `:32-50`) — в собранном приложении (подсистема `WINDOWS_GUI`) консоли нет, файл остаётся единственным следом сбоя; инспектор — только по `--dev` или `NEXUS_DEVTOOLS=1` и только после `did-finish-load` (`:66`, `:460-465`); отсутствие `dist/index.html` даёт не пустое белое окно, а страницу с объяснением в самом окне плюс запись в stderr (`:96-113`, `:467-473`).

## 8. Сборка

**Single-file и вшитый wasm.** `vite.config.ts:77`: плагины `wasmInlinePlugin()`, `react()`, `tailwindcss()`, `viteSingleFile()`, `cspPlugin()`, плюс явный `base: "./"` (`:76`) — раньше base попутно выставлял `viteSingleFile`, и полагаться на побочный эффект чужого плагина нельзя: абсолютный base увёл бы ссылки от корня и под `file://` в Electron, и под origin `https://localhost` в контейнере Capacitor. Результат — один `dist/index.html` с inline-встроенными JS и CSS; Electron открывает его по `file://`. WASM встраивается собственным плагином `wasmInlinePlugin` (`vite.shared.ts:14-34`): он перехватывает импорт с суффиксом `?wasm-inline` и отдаёт `export default "data:application/wasm;base64,…"`. Причина отдельного плагина — в комментарии `vite.shared.ts:4-8` и в `src/storage/wasmAsset.ts`: стандартный `?inline` помечает импорт ресурса как модуль (`?import`), и Vite пытается разобрать бинарный `.wasm` как JavaScript — dev-сервер отвечает 500. Единственный потребитель — `import wasmInline from "sql.js/dist/sql-wasm.wasm?wasm-inline"` (`wasmAsset.ts:9`), далее `base64ToBytes` → `initWasm({ wasmBinary })` (`sqlite.ts:42-54`). Фолбэк на `sql-asm.js` (`sqlite.ts:51`) объясняет ~2.9 МБ итогового бандла.

**CSP.** Плагин `cspPlugin` объявлен с `apply: "build"` (`vite.config.ts:53-67`) — в dev-режиме политика сломала бы HMR-клиент. Содержимое (`:38-51`): `default-src 'none'; base-uri 'none'; object-src 'none'; form-action 'none'; script-src 'unsafe-inline' 'wasm-unsafe-eval' data: blob: file: https://cdn.jsdelivr.net; style-src 'unsafe-inline' data: file:; img-src / font-src / media-src 'self' data: blob: file:; connect-src 'self' data: blob: file: https://cdn.jsdelivr.net; worker-src / frame-src 'self' blob: data:`. Обоснования: `'unsafe-inline'` — весь бандл inline; `'wasm-unsafe-eval'` — без него блокируется компиляция модуля `sql.js`; `blob:` / `data:` — воркер tesseract.js и base64-wasm; `file:` — под `file://` origin `'self'` не совпадает с файловыми URL; `cdn.jsdelivr.net` — единственный внешний хост, и он нужен **в двух директивах**: в `connect-src` за сами данные (wasm-ядро и `*.traineddata`, их грузит сам воркер), в `script-src` потому, что воркер создаётся из `blob:`-URL и его тело делает `importScripts("https://cdn.jsdelivr.net/…/worker.min.js")`, а `importScripts` проверяется по `script-src` унаследованной им политики. Без второго воркер не стартует — одинаково под `file://` в Electron и под origin `https://localhost` в контейнере Capacitor. `worker-src` править не нужно: воркер создаётся из `blob:`, а он уже разрешён.

**Почему node-модули нельзя объявлять external.** `fs`, `path`, `child_process`, `electron` оставлены в `optimizeDeps.exclude` (`vite.config.ts:70-72`, `vite.dev.config.ts:23-25`), но **не** в `external`. Причина в комментарии `vite.config.ts:75-81`: external оставляет в бандле голый `import "fs"`, и страница падает при загрузке с «Failed to resolve module specifier "fs"». В dev это скрыто заглушками Vite, в single-file сборке — нет. Главный процесс Electron — отдельные `.cjs` и в эту сборку не входит. `define: { "process.env": {}, global: "globalThis" }` гасит обращения к Node-окружению.

## 9. Анимации и производительность

**Delta-time вместо покадровых значений.** `src/animations/ticker.ts`: `createTicker` (`:36-72`) — один rAF-цикл на анимацию; скорость задаётся в единицах в секунду, кадр даёт `delta = min(max(ts - last, 0), maxDelta)` где `MAX_DELTA_MS = 100` (`:8`). Прямой запрет записан в комментарии `:79-83`: `x += 5` — скорость зависит от частоты кадров; `x += speed * dt / 1000` — пикселей в секунду. `createValueTransition` (`:117-137`) переводит значение за фиксированное wall-clock время: на 60 и 144 Гц финиширует с одинаковым значением. `stepLinear` имеет собственный лимит длинного кадра с тем же порогом по умолчанию — иначе лимит цикла и лимит шага разошлись бы. Тесты (`tests/animations.test.ts`) проверяют совпадение смещения на 60 и 144 Гц, одинаковое wall-clock время, регрессию «фиксированное смещение за кадр» и лимит длинного кадра.

**Страховка по таймеру.** `requestAnimationFrame` в фоновой вкладке не срабатывает. Там, где появление зависело только от rAF, добавлен таймер: `charts.tsx:39-46`, `:154-158`, `:252` — `requestAnimationFrame(show)` **и** `setTimeout(show, 60)`, отменяемые при размонтировании. Без этого график в фоновой вкладке навсегда оставался в стартовом состоянии (пустые столбцы).

**Почему `scaleY`/`scaleX`, а не `y`/`height`/`width`.** Анимация layout-свойств на каждом кадре пересчитывает раскладку и вызывает reflow. Поэтому столбцы графика рисуются **сразу в конечных координатах** и «вырастают» через `transform: scaleY()` с `transformBox: "fill-box"`, `transformOrigin: "bottom"` (`charts.tsx:90-113`); полоса прогресса анимируется `scaleX` (`waapi.ts:217-236`), причём конечное значение сразу пишется в inline-стиль, а начальное берётся из предыдущей записи `lastScaleX` — иначе каждый показ стартовал бы с CSS-нуля `scaleX(0)`; CSS-анимации `scanmove`, `scan-sweep`, `glow-drift` переведены с `top` на `transform` (`index.css:1514-1531`). Осознанное исключение из правила «только transform/opacity»: `stroke-dasharray` у секторов пончика (`charts.tsx:192-196`) — paint-свойство SVG, reflow оно не вызывает.

**Управление анимациями** (`src/animations/waapi.ts`): `resolveMotionPlan` (`:50-62`) — при `reduced` или `lowEnd` анимация **выключается целиком**, и деградацию нельзя отменить конкретным запросом (`lowEnd` складывается через `||`); `applyFinal` (`:41`, `:104-109`) — при выключенной анимации применяется конечное состояние, иначе «анимация выключена» означало бы «ничего не применено» и полоса залипла бы на `scaleX(0)` с ложными нулями в бюджете; `ownAnimations` (`WeakMap<Element, Set<Animation>>`, `:84-97`) — `animate()` отменяет только собственные анимации модуля, поскольку с `fill: "both"` старая навсегда остаётся в `getAnimations()`, конфликтует по каскаду и удерживает композитный слой; `stagger` (`:257-277`) — появление списков с лимитом одновременных анимаций (по умолчанию 24, у тостов 6 при `stepMs: 45`, `ui.tsx:843-853`), элементы за лимитом не «пропадают», а получают `applyFinal`; `pressPop` (`:202-207`) требует `fill: "none"` от вызывающего, иначе конечный `scale(1)` навсегда перекроет CSS-состояния (hover/`:active`).

**Деградация в CSS.** `@media (prefers-reduced-motion: reduce)` (`index.css:1543-1555`) обнуляет `animation-duration`, `animation-iteration-count`, `transition-duration` и **`animation-delay`**: у `.rise-in` задержка задана инлайном до 380 мс при `fill-mode: both`, поэтому без обнуления карточки оставались невидимыми на всё это время. `html[data-perf="low"]` (`:1562-1661`) отключает `backdrop-filter` на карточках и панелях, тени, фоновые слои (`.app-bg-grid`, `.app-bg-glow*`, `.app-bg-scan`, `.scan-veil`) целиком, анимации `pulse-soft` / `spin` / `view-anim` / `rise-in` / `modal-overlay` / `price-flash` / `status-dot` / `scan-line`, переход полосы прогресса, переходы строк, разделители у чётных строк, hover-подсветку строк (кроме выделенных, класс `.selected`) и подпись «источник операции» (`.jcell-src`). Суммы, даты и статусы не трогаются — это данные. `html[data-motion="reduced"]` (`:1607-1616`) дублирует отключение для системной настройки, включая переход `.progress-fill`: CSS-переход сгладил бы «мгновенно» применённое значение на 0.65 с, то есть снова сделал бы движение. Отдельный блок `@media (min-resolution: 120dpi/192dpi)` (`:1671-1684`) сокращает длительности на экранах высокой плотности: на 2× каждый кадр обходится вчетверо дороже по физическим пикселям (это плотность пикселей, а не частота кадров).

**Ленивая загрузка экранов.** `src/App.tsx:16-23` — 6 экранов через `React.lazy` + `Suspense`; `Dashboard` остаётся в основном бандле, потому что показывается сразу после старта. Сканер (`jsqr` + `tesseract.js`) в стартовый бандл не попадает. Заглушка `ViewSkeleton` (`App.tsx:44-55`) принципиально без анимаций.

## 10. Темы и оформление

Три темы через `data-theme` на `<html>`: `cyberpunk`, `dark`, `light` (`index.css:6`, `:30`, `:51`; список с образцами — `lib/constants.ts:38-42`). Токены задаются один раз на тему и используются везде: `--bg`, `--card`, `--card-solid`, `--line`, **`--card-line`**, `--card-text`, `--muted`, `--text`, `--accent`, `--pink`, `--ok`, `--warn`, `--danger`, `--on-accent`, `--glow`. `--line` (9% белого) был почти не виден, поэтому граница карточки вынесена в отдельный `--card-line` (17% белого в cyberpunk, 15% в dark, `#d2d9e6` в light) и рисуется в два слоя: 1px линии + мягкий внутренний блик (`index.css:508-521`). `--ink` и `--ink-2` — алиасы `--text` и `--muted`, введённые, чтобы навигация и футер не остались без цвета.

**Почему контур шестиугольника рисуется через `box-shadow: inset`** (`index.css:462-479`). `clip-path: polygon(...)` обрезает **всё**, включая обычную рамку: у шестиугольника срезаются углы, и `border` выглядит «обрубленной» — линия пропадает ровно на диагоналях.

```css
.hex {
  --hex-ring: 1.5px;
  --hex-ring-color: currentColor;
  clip-path: polygon(50% 0, 100% 25%, 100% 75%, 50% 100%, 0 75%, 0 25%);
  box-shadow: inset 0 0 0 var(--hex-ring) var(--hex-ring-color);
}
```

Внутренняя тень обрезается тем же `clip-path` и идёт ровно по контуру фигуры, включая срезанные углы. Следствия, зафиксированные в коде: разметка задаёт **только цвет** (`currentColor` = цвет категории) и заливку; рамку в разметке ставить нельзя — иначе поверх inset-тени ляжет вторая тонкая линия. Варианты `.hex-sm` (1px), `.hex-muted` (контур 40% прозрачности), `.hex-logo` (светлее) задают только толщину и насыщенность. Срезанный угол карточки `.cut` (`:523-539`) решён так же, но локально: только `[data-theme="cyberpunk"] .cut` получает `box-shadow: inset …` по срезу, а в `dark` и `light` угол не срезан (`clip-path: none`) и остаётся внешняя тень карточки.

**Светлая тема.** Цвета категорий насыщенно-светлые (`#00FF87`, `#00D4FF` — `lib/constants.ts:9-25`), и на белой карточке контур, построенный из них, почти не виден. Поэтому в `[data-theme="light"]` контур смешивается с чернилами темы: `color-mix(in srgb, currentColor 62%, #1a1a2e)` (`.hex`), `82%` для логотипа, `40%` для приглушённого (`index.css:493-504`) — граница читается, а фигура остаётся цветной. В light также переопределены тени карточки, фон ввода, фон опций `select`, hover категорий и подложка модалки.

Прочие решения по вёрстке, зафиксированные в коде: тултипы графиков клампятся по ширине и не выходят за карточку (`charts.tsx:10-23`); кольцо и легенда «расходов по категориям» всегда идут друг под другом, а не в ряд (карточка на дашборде ~310 px); `viewport-fit=cover` в `index.html:8` для безопасной зоны на телефонах с вырезом.

### 10.1 Мобильная вёрстка: что оказалось не проверено до устройства

Проверено на **Infinix X6858, Android 16 (SDK 36)**, 1080×2436 при плотности 440 —
≈393 CSS-пикселя по ширине. Ширина и есть тот размер, под который вёрстка
телефона обязана быть верной: 9 пунктов навигации в 393 пикселя — это около 2,5
экрана горизонтальной прокрутки. Всё, что ниже, не было видно ни в десктопном
браузере, ни в Electron.

**Стек оверлеев по `z-index`.** Порядок задан явно, и каждый уровень отвечает за
своё; путаница между ними и стоила 4 секунды недоступной навигации.

| Уровень | Что это | Где |
|---------|---------|-----|
| `-1` | `.app-bg` — сетка, свечения, сканирующая линия; `pointer-events: none`, декоративный слой | `index.css:151-157` |
| `30` | `.sidebar` — боковое меню, только на десктопе | `index.css:235`, `z-index` на `:249` |
| `40` | `.mobile-topbar` — липкая шапка, только на телефоне | `index.css:331-344`, `z-index` на `:335` |
| `45` | `.mobile-nav` — нижняя лента вкладок | `index.css:295-314`, `z-index` на `:301` |
| `50` | `Modal` и `BottomSheet` (шторка «Ещё») | `ui.tsx:421`, `:551` |
| `70` | `ToastHost` — всплывающие сообщения | `ui.tsx:1014` |
| `90` | онбординг | `Onboarding.tsx:88` |

Тост стоит **выше** ленты (`70` против `45`), поэтому одного `z-index`
недостаточно: на телефоне контейнер тостов позиционируется над лентой —
`@media (max-width: 900px) div[aria-live="polite"]` (`index.css:1703-1710`) даёт
`bottom: calc(62px + var(--sab))` и боковые отступы от `--sal/--sar`. Селектор
берёт не служебные классы Tailwind (`bottom-4`, `right-4`), а признак
доступности: он переживает перегенерацию классов. Побочная выгода — контейнер
объявлен `aria-live="polite"`, то есть всплывающие сообщения читает скринридер.

**Безопасные зоны.** Переменные `--sat`, `--sar`, `--sab`, `--sal` в `:root`
(`index.css:7-17`) читают `env(safe-area-inset-*, 0px)`. Обоснование в комментарии
там же: при `targetSdk 35+` (у нас 36) приложение рисуется под системными
панелями, и без верхнего отступа липкая шапка уезжала под строку состояния и под
вырез. Применяются в `.mobile-topbar`, `.mobile-nav`, `.app-main`, контейнере
тостов и панели шторки. Фолбэк `0px` — правило совместимости: на десктопе и в
старых WebView значения равны нулю и ничего не меняется.

**Касательный ввод — отдельный блок `@media (pointer: coarse)`**
(`index.css:1721-1747`), и это не стилевое предпочтение, а два класса правок:

| Правило | Что | Зачем |
|---------|-----|-------|
| `min-height: 44px` для `.btn`, `.btn-sm`, `.btn-icon`, `.chip`, `.segmented-btn`, `.page-btn`, `.mobile-nav-btn`; `min-width: 44px` для иконок и кнопок страниц | Зона нажатия не меньше 44 CSS-пикселей | У иконок-кнопок было 30 — палец промахивался по углам ячеек |
| `font-size: 1rem` для `.input`, `select.input`, `.price-edit`, `.chip-date` | Кегль поля ≥ 16 px (было 14,4) | Blink на Android увеличивает visual viewport, если кегль меньше 16 пикселей, и отдаляет назад при потере фокуса — выглядит как «вспышка зума». На 16 пикселях авто-зум не включается |
| `scroll-margin-block: 24px` для полей, плиток категорий и выбора категории | Поле при автопрокрутке к нему | Не липнет к краю модалки |

Десктоп блоком не задет: вёрстка настраивалась мышью, и общие правила трогать
нельзя. Сюда же относится нижняя лента: пять пунктов, сетка
`grid-auto-flow: column` с `grid-auto-columns: minmax(0, 1fr)` — `1fr` без
`minmax(0, …)` возвращал бы горизонтальную прокрутку из-за длинной подписи,
иконка над подписью, `min-height: 48px`, бейдж неподтверждённых на углу иконки
(рядом с подписью он занял бы третью строку и съел высоту зоны нажатия).

**Уровень `mid` наконец описан.** Он существовал в `capabilities.ts`, но ни одно
правило CSS его не упоминало: телефон со средним запасом памяти получал полные
эффекты — размытие на каждой карточке и два фоновых свечения с `will-change`.
`html[data-perf="mid"]` (`index.css:1749-1760`) скрывает `.app-bg-glow*` и
снимает `backdrop-filter` с `.card`. В правила для `low` добавлены `.mobile-nav` и
`.mobile-topbar` — без них лента и шапка оставались размытыми.

**Указатель на графике.** `src/components/charts.tsx` слушает
`onPointerEnter` / `onPointerMove` / `onPointerLeave` / `onPointerCancel` и
задаёт `touchAction: "pan-y"`: раньше были события мыши, и на касании тултип
залипал, а график нельзя было «протереть». `pan-y` отдаёт вертикальную
прокрутку страницы жесту, горизонтальную ведёт сам.

## 13. Известные архитектурные риски

| Риск | Суть | Что сделано сейчас |
|------|------|--------------------|
| **Вся БД в памяти** | `sql.js` держит базу в памяти рендерера, а `persist()` после **каждой** успешной транзакции делает `db.export()` — полный образ — и пишет его целиком. Стоимость линейна по числу записей (16.2 мс на 1000), образ растёт (592 КБ на 1000) | `SqlDriver` разделён так, что замена на нативный драйвер локальна; есть `VACUUM` и дебаунс автосохранения 500 мс. Для сотен тысяч записей нужен нативный драйвер |
| **WAL не работает** | На in-memory базе `journal_mode` остаётся `memory`; параллельные чтения при записи не получаются | Применяется в `try/catch`, честно отображается в настройках, покрыто тестом |
| **Очистка данных приложения на мобильном стирает IndexedDB** | На Windows файл в `userData` переживает очистку кэша; в Android WebView очистка данных ОС удаляет IndexedDB вместе с базой. Второй путь потери — Google Backup: он забирал всю приватную папку, и база могла восстановиться на другом устройстве молча | Бэкап закрыт: `allowBackup="false"` плюс `res/xml/{data_extraction_rules,backup_rules}.xml` запрещают и `cloud-backup`, и `device-transfer`. **Побочный эффект: экспорт в JSON стал обязательным** — восстановить базу больше нечем, кроме нативной файловой БД |
| **Глифы валют зависят от системного шрифта** | В системном шрифте Infinix X6858 / Android 16 нет ₽ (U+20BD), суммы рисовались как `557 885 ▯`; `Intl.NumberFormat` со `style: "currency"` подставляет символ сам и подменить его после нельзя | `readSymbol()` (`src/lib/utils.ts:136`) проверяет глиф измерением ширины в канвасе против U+FFFF и возвращает текстовую замену («руб.», «USD», «EUR», «GBP»); `formatNumber` форматирует число отдельно. Раздел 5.3 |
| **APK проверен на одном устройстве** | Раньше не запускался вовсе: эмулятор в среде собрать было нечем, сверялся только состав пакета. Исправления вёрстки, сделанные под ≈393 CSS-пикселя, могут не подойти другому экрану | Проверено на Infinix X6858, Android 16: запуск, база, «Назад», экспорт, настройки. **Требует проверки:** другие устройства, камера и OCR (нужен `cdn.jsdelivr.net`), альбомная ориентация, predictive-back, системное меню «Поделиться» |
